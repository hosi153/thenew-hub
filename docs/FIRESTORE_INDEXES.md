# Firestore 쿼리와 인덱스 요구사항

`docs/PERFORMANCE_REFACTORING_PLAN.md` 4단계 "필요한 정렬·필터 조합에 맞춘 Firestore 복합
인덱스를 문서화한다" 항목의 결과물입니다.

## 결론부터

**현재 앱이 실행하는 모든 쿼리는 Firestore가 자동으로 만들어주는 단일 필드 인덱스만으로
충분합니다. 수동으로 복합 인덱스(composite index)를 만들 필요가 없습니다.**

이건 우연이 아니라, 쿼리를 설계할 때 의도적으로 "여러 필드를 동시에 필터링하지 않는다"는
원칙을 지켰기 때문입니다. Firestore는 다음 두 경우엔 복합 인덱스 없이도 동작합니다:

- 같은 필드에 대한 범위(`>=`, `<`, `<=`) 조건을 여러 개 걸어도 괜찮음
- 필터링에 쓴 필드와 정렬(`orderBy`)에 쓴 필드가 같으면 괜찮음

## 컬렉션별 실제 쿼리 목록

### `hallSchedule` (홀 일정)

| 쿼리 | 위치 | 인덱스 필요 여부 |
|---|---|---|
| `where('datetime','>=',now).orderBy('datetime').limit(20)` | 목록 무한스크롤 (다가오는 일정 페이지네이션) | ❌ 불필요 — 필터·정렬 필드가 동일 |
| `where('datetime','==','')` | "날짜 미정" 항목 조회 | ❌ 불필요 — 단일 필드 |
| `where('datetime','>=',월시작).where('datetime','<',월끝)` | 캘린더 월별 조회 | ❌ 불필요 — 같은 필드의 범위 조건 두 개 |
| `.limit(1)` (필터 없음) | 컬렉션 비어있는지 확인 | ❌ 불필요 |
| 필터 없음 전체 조회 (검색/필터/지난 식 보기 활성화 시) | `loadAllSchedules()` | ❌ 불필요 |

### `matchingCodes` (짝꿍코드)

| 쿼리 | 위치 | 인덱스 필요 여부 |
|---|---|---|
| `orderBy(FieldPath.documentId()).limit(20)` | 목록 무한스크롤 | ❌ 불필요 — 문서 ID 정렬은 항상 기본 제공 |
| `.limit(1)` (필터 없음) | 컬렉션 비어있는지 확인 | ❌ 불필요 |
| 필터 없음 전체 조회 | `loadAllMatchingCodes()` | ❌ 불필요 |

### `prepChecklist` (체크리스트)

| 쿼리 | 위치 | 인덱스 필요 여부 |
|---|---|---|
| 필터 없음 전체 조회만 존재 (`loadAllChecklists()`) | 소규모 컬렉션이라 페이지네이션 자체를 안 씀 | ❌ 불필요 |

## 앞으로 복합 인덱스가 필요해지는 경우

아래처럼 **서로 다른 두 필드**를 동시에 필터링/정렬하는 쿼리를 새로 추가하면 그때는
Firestore 콘솔(또는 에러 메시지에 뜨는 링크)에서 복합 인덱스를 만들어야 합니다:

- 예: "제니스홀만, 다가오는 일정만" 같은 홀 필터 + 날짜 필터를 **서버 쿼리로** 동시에 걸고
  싶어지는 경우 → `where('hall','==','제니스홀').where('datetime','>=',now)` 형태는
  `hall` + `datetime` 복합 인덱스가 필요합니다. (지금은 홀 필터가 걸리면 클라이언트에서
  전체 로드 후 걸러내는 방식으로 우회하고 있어서 인덱스가 필요 없습니다 — 짝꿍코드 카테고리
  필터도 동일한 방식입니다.)
- 예: 짝꿍코드를 카테고리별로 서버에서 페이지네이션하고 싶어지는 경우 →
  `category` + 정렬 기준 필드의 복합 인덱스가 필요합니다.

이런 쿼리를 추가하게 되면, 로컬 개발 중 첫 실행 시 Firestore가 콘솔 콘솔에서 인덱스를
자동 생성할 수 있는 링크를 에러 메시지로 던져줍니다. 그 링크로 만든 인덱스는
`firestore.indexes.json`으로 내보내 이 저장소에 커밋해두는 걸 권장합니다(지금은 해당 파일이
없습니다 — 아직 복합 인덱스를 쓰는 쿼리가 없기 때문입니다).
