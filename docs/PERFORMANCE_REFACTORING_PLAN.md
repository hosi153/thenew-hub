# 성능 개선 리팩터링 계획

## 진행 현황 (수시 갱신)

| 단계 | 상태 | 비고 |

## 1. 목적

현재 기능과 GitHub Pages 배포 방식을 유지하면서 초기 로딩, 데이터 저장, 검색·캘린더 렌더링 속도를 개선하고 기능별로 안전하게 유지보수할 수 있는 구조로 전환한다.

이번 리팩터링의 기본 원칙은 다음과 같다.

- GitHub Pages에서 계속 정적 웹앱으로 배포한다.
- 일정, 짝꿍코드, 체크리스트와 비밀번호 입력 기능을 유지한다.
- 기존 SHA-256 및 PBKDF2 비밀번호 데이터와 Firestore 문서 형식을 깨지 않는다.
- 각 단계는 별도 커밋으로 배포하고 문제가 생기면 해당 단계만 되돌릴 수 있게 한다.
- 구조 변경과 기능 변경을 한 커밋에 섞지 않는다.

## 2. 현재 상태와 병목

2026-08-31 기준으로 확인한 내용이다.

| 영역 | 현재 상태 | 영향 |
| --- | --- | --- |
| 앱 구조 | `index.html` 2,967줄, 약 149KB에 HTML·CSS·JavaScript 집중 | 변경 영향 파악과 기능별 테스트가 어려움 |
| Firebase | compat SDK 두 파일을 외부 CDN에서 로드 | 초기 파싱 비용과 전역 API 의존성이 큼 |
| 저장 | SDK 쓰기를 최대 7초 기다린 후 REST로 재시도 | SDK 채널이 막힌 환경에서 모든 저장이 약 7초 이상 지연될 수 있음 |
| 저장 제한 | SDK 7초 + REST 10초, 호출부 최대 20초 | 실패 판단과 사용자 피드백이 늦음 |
| 비밀번호 | 신규 생성 시 PBKDF2-SHA256 210,000회 수행 | 보안상 필요한 비용이지만 저성능 모바일에서 추가 지연 발생 가능 |
| 목록 조회 | 검색·필터 시 `ensure*FullyLoaded()`가 전체 컬렉션을 읽음 | 데이터 증가에 따라 네트워크·메모리·렌더링 비용 증가 |
| 렌더링 | 문자열 기반 `innerHTML` 전체 교체가 많음 | 데이터가 커질수록 불필요한 DOM 재생성 증가 |
| 배포 | 빌드·검증 자동화 없음 | 압축, 캐시 무효화, 배포 전 회귀 검증이 제한됨 |

실제 사용자 환경의 지표는 아직 수집하지 않았으므로 위 내용은 코드 기반 진단이다. 0단계에서 측정값을 확보한 후 목표와 우선순위를 다시 확인한다.

## 3. 목표 지표

모바일 중급 기기와 일반적인 4G/Wi-Fi 환경을 기준으로 한다.

| 지표 | 목표 |
| --- | --- |
| 저장 성공 응답 | 정상 네트워크 p50 1초 이하, p95 2.5초 이하 |
| 대체 전송 경로 진입 시 저장 | p95 4초 이하 |
| 초기 화면 LCP | p75 2.5초 이하 |
| 사용자 입력 후 화면 갱신 | 100ms 이내 |
| 검색 입력 처리 | 150ms 디바운스 후 100ms 이내 결과 표시 |
| 모바일 레이아웃 | 320px 이상에서 가로 스크롤 없음 |
| 회귀 검증 | 정적 테스트, 핵심 기능 E2E, Firebase Emulator 테스트 통과 |

지표에는 Firebase 요청 시간, 비밀번호 해싱 시간, DOM 갱신 시간을 각각 분리해 기록한다. 비밀번호 원문이나 사용자 입력값은 로그에 남기지 않는다.

## 4. 목표 구조

Vite를 빌드 도구로 사용하되 결과물은 정적 파일만 생성한다. 따라서 GitHub Pages 배포는 계속 가능하다.

```text
index.html
src/
  main.js
  config/
    firebase.js
  data/
    firestore-rest.js
    repositories.js
    transport.js
  features/
    schedule/
      api.js
      state.js
      view.js
    codes/
      api.js
      state.js
      view.js
    checklist/
      api.js
      state.js
      view.js
  security/
    password.js
  ui/
    modal.js
    navigation.js
    toast.js
  styles/
    tokens.css
    base.css
    components.css
    features/
tests/
```

한 화면 안에서 하단 메뉴로 이동하는 현재 사용 경험은 유지한다. 기능 코드는 ES 모듈과 동적 `import()`로 나눠 처음 방문한 기능만 불러온다. 별도 URL이 필요해지면 GitHub Pages에서 새로고침 404가 발생하지 않도록 해시 라우팅을 사용한다.

## 5. 단계별 실행 계획

### 0단계: 기준선과 안전망 확보 — ⏸ 부분/보류

- 저장, 조회, PBKDF2, 렌더링 시간을 `performance.mark()`로 구분해 개발 모드에서 측정한다.
- 320px, 375px, 430px 모바일 뷰포트의 가로 넘침 검사를 자동화한다.
- 일정·코드·체크리스트 생성, 수정, 삭제와 기존 비밀번호 검증을 E2E 시나리오로 정의한다.
- Firebase Emulator용 테스트 설정을 추가해 운영 데이터 없이 저장 경로를 검증한다.
- 현재 배포본과 성능 측정 결과를 기준선으로 기록한다.

완료 조건:

- 최적화 전 저장 지연을 SDK, REST, PBKDF2 구간별로 설명할 수 있다.
- 기존 8개 정적 테스트와 핵심 E2E 시나리오가 통과한다.

### 1단계: 저장 체감 속도 개선 — ✅ 완료 (사용자 확인됨)

- 쓰기 전송 계층을 `transport.js`로 격리한다.
- 현재 세션에서 SDK 타임아웃이 한 번 발생하면 이후 쓰기는 REST를 우선하도록 상태를 기억한다.
- 최초 SDK 시도 예산을 7초에서 1.5~2초 범위로 줄이고 실제 측정값으로 확정한다.
- 동일 문서 ID에 대한 `set`을 유지해 늦게 완료된 SDK 요청과 REST 재시도가 중복 데이터를 만들지 않게 한다.
- 저장 단계별 상태를 `비밀번호 처리 중`, `저장 중`, `연결 재시도 중`으로 구분한다.
- REST 요청에는 `AbortController`를 적용하고 네트워크 오류와 권한 오류를 구분한다.
- PBKDF2 210,000회와 기존 해시 호환성은 유지하되 Web Crypto 소요 시간을 별도 측정한다.

완료 조건:

- SDK 채널이 차단된 테스트에서도 저장 성공이 4초 이내다.
- 생성·수정·삭제 실패 시 낙관적 UI 변경이 모두 원복된다.
- 동일 요청의 지연 완료가 문서 중복을 만들지 않는다.

### 2단계: 빌드 기반과 정적 자산 분리 — ✅ 완료

- Vite와 `npm` 스크립트(`dev`, `build`, `test`, `preview`)를 추가한다.
- 인라인 CSS를 `src/styles/`로 옮기되 시각적 변경은 하지 않는다.
- 인라인 JavaScript를 우선 단일 `src/main.js`로 옮겨 동작을 그대로 유지한다.
- Firebase 설정값은 별도 설정 모듈로 옮긴다. 클라이언트 API 키는 비밀 인증 수단으로 취급하지 않되 Firebase 허용 도메인과 Firestore Rules를 점검한다.
- `vite.config.js`의 GitHub Pages 기준 경로를 저장소명 `/thenew-hub/`에 맞춘다.

완료 조건:

- `npm run build` 결과인 `dist/`를 정적 서버에서 실행할 수 있다.
- 빌드 전후 화면과 데이터 동작이 동일하다.
- 생성된 해시 파일명으로 브라우저 캐시 무효화가 자동 적용된다.

### 3단계: 기능 모듈화 — ✅ 완료

- [x] Firebase/REST, 비밀번호, 모달, 토스트 같은 공통 기능부터 분리한다. → `web/src/config/firebase.js`, `web/src/security/password.js`, `web/src/data/firestore-rest.js`, `web/src/ui/toast.js`, `web/src/ui/modal.js` 완료
- [ ] Firebase compat 전역 API를 필요한 기능만 가져오는 modular API로 단계적으로 교체한다. (compat SDK CDN 로드 방식 유지 중, 아직 미착수)
- [x] 일정 기능을 API·상태·화면 모듈로 나눈다. → `web/src/features/schedule/` 완료
- [x] 짝꿍코드 기능을 API·상태·화면 모듈로 나눈다. → `web/src/features/codes/` 완료
- [x] 체크리스트를 API·상태·화면 모듈로 나눈다. → `web/src/features/checklist/` 완료
- [ ] 인라인 `onclick`, `oninput`, `onchange`를 이벤트 위임 또는 모듈 내부 리스너로 교체한다. (2단계에서 만든 `window.함수명 = 함수명` 임시 노출 방식을 계속 사용 중)
- [ ] 전역 상태를 기능별 상태 객체로 제한하고 모듈 간 직접 변경을 금지한다.
- [ ] 체크리스트처럼 초기 화면에 필요 없는 기능은 동적으로 불러온다.

완료 조건 (아직 미충족):

- 기능 모듈이 다른 기능의 내부 변수에 직접 접근하지 않는다.
- 초기 진입 시 사용하지 않은 기능 번들이 다운로드되지 않는다.
- 기존 Firestore 필드와 비밀번호 검증 결과가 동일하다. — 비밀번호 검증 로직 자체는 이동만 했으므로 동일함을 정적 검증(테스트)으로 확인함

### 4단계: 데이터 접근 최적화 — ✅ 완료

- [x] 일정 목록은 현재 페이지, 캘린더는 표시 월 범위만 Firestore 쿼리한다. (3단계 이전부터 이미 구현되어 있었음, 재확인함)
- [x] 짝꿍코드와 체크리스트는 커서 기반 페이지네이션을 공통 저장소 계층으로 통합한다. → web/src/data/collection-repository.js (체크리스트는 설계상 페이지네이션 없이 loadAll만 사용)
- [x] 검색 요구사항과 Firestore 쿼리 한계를 확인해, 소규모 데이터는 세션 캐시 검색을 사용하고 임계치를 넘으면 검색 인덱스 도입을 별도 결정한다. (검색/필터/지난식보기 활성화 시 전체 로드 후 클라이언트 검색 — 이미 구현되어 있었음)
- [x] 동일 컬렉션의 중복 요청을 합치고 진행 중 Promise와 마지막 성공 결과를 캐시한다. → collection-repository.js의 loadAll()에 내장
- [x] 저장 성공 시 전체 재조회 대신 해당 로컬 항목만 갱신한다. (이미 구현되어 있었음, 재확인함)
- [x] 필요한 정렬·필터 조합에 맞춘 Firestore 복합 인덱스를 문서화한다. → docs/FIRESTORE_INDEXES.md (현재는 복합 인덱스가 필요한 쿼리가 없음을 확인하고 문서화)

완료 조건:

- 일반 목록·캘린더 진입이 전체 컬렉션 조회를 발생시키지 않는다.
- 페이지 이동과 필터 변경 중 동일 요청이 중복 전송되지 않는다.
- 데이터가 증가해도 한 번의 DOM 렌더링 대상 수가 상한을 가진다.

### 5단계: 렌더링과 상호작용 최적화 — ⬜ 미착수

- 검색 입력에 150ms 디바운스를 적용한다.
- 목록 전체 `innerHTML` 교체를 키 기반 부분 갱신 또는 `DocumentFragment` 렌더링으로 전환한다.
- 캘린더 월별 계산 결과와 정렬 결과를 데이터 변경 시에만 무효화한다.
- 긴 목록은 페이지네이션을 유지하고 필요 시 가상 스크롤 도입 여부를 측정 후 결정한다.
- 모달 포커스, 키보드 조작, `prefers-reduced-motion` 지원을 회귀 테스트에 포함한다.

완료 조건:

- 검색과 필터 조작이 목표 응답 시간 안에 완료된다.
- 동일 상태 재렌더링 시 불필요한 네트워크 요청과 전체 DOM 교체가 없다.
- 모바일 접근성과 가로 넘침 테스트가 통과한다.

### 6단계: GitHub Pages 자동 배포 — ✅ 완료

- GitHub Actions에서 설치, 테스트, 빌드 후 `dist/`만 Pages에 배포한다.
- pull request에서는 테스트와 빌드만 실행하고 `main` 반영 시 배포한다.
- Firebase 허용 도메인에 실제 Pages 도메인을 확인한다.
- 배포 후 정적 자산 404, Firebase 연결, 핵심 생성·수정 흐름을 스모크 테스트한다.
- 직전 성공 배포와 커밋을 기록해 롤백 절차를 문서화한다.

완료 조건:

- 수동 파일 복사 없이 `main` 커밋으로 배포된다.
- 저장소 하위 경로에서 CSS, JavaScript, 동적 모듈 경로가 모두 정상이다.
- 실패한 테스트나 빌드는 배포되지 않는다.

1. `test: 성능 기준선과 핵심 E2E 추가`
2. `fix: Firestore 저장 폴백 지연 단축`
3. `chore: Vite 정적 빌드 환경 구성`
4. `refactor: 스타일과 애플리케이션 스크립트 분리`
5. `refactor: 공통 데이터와 비밀번호 모듈 분리`
6. `refactor: 일정 기능 모듈화`
7. `refactor: 짝꿍코드와 체크리스트 모듈화`
8. `perf: Firestore 조회와 렌더링 최적화`
9. `ci: GitHub Pages 자동 배포 구성`

각 커밋에서 정적 테스트, 관련 단위 테스트, 핵심 E2E를 다시 실행한다. 대규모 파일 이동과 동작 변경은 같은 커밋에 포함하지 않는다.

## 7. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 모듈 분리 중 전역 실행 순서 변경 | 먼저 파일만 이동하고 이후 작은 단위로 의존성 주입 |
| REST와 SDK 요청이 모두 늦게 성공 | 동일 문서 ID와 멱등적인 쓰기 유지, 요청 상태 기록 |
| 기존 비밀번호 데이터 검증 실패 | SHA-256·PBKDF2 고정 벡터 테스트와 마이그레이션 없는 호환 경로 유지 |
| GitHub Pages 하위 경로 자산 404 | Vite `base` 설정 및 배포 후 경로 스모크 테스트 |
| Firestore 읽기 비용 증가 | 월 범위·페이지 단위 쿼리, 요청 캐시, Emulator 쿼리 테스트 |
| 리팩터링 중 UI 회귀 | 주요 모바일 너비 스크린샷과 가로 넘침 자동 검사 |

## 8. 이번 계획에서 제외하는 항목

- Firebase Auth나 별도 서버 도입
- 비밀번호 기능 제거 또는 기존 비밀번호 데이터 일괄 변경
- React, Vue 등 UI 프레임워크 전환
- 디자인 전면 개편
- Firestore 컬렉션과 필드의 비호환 변경

이 항목들은 현재 성능 개선에 필수적이지 않으며 범위와 위험을 불필요하게 키우므로 별도 의사결정 후 진행한다.

## 9. 착수 우선순위

가장 먼저 0단계로 실제 시간을 측정하고, 곧바로 1단계의 저장 전송 경로를 개선한다. 이는 구조를 크게 바꾸지 않고도 현재 사용자가 느끼는 저장 지연을 가장 빠르게 줄일 수 있다. 이후 빌드 기반과 모듈 분리를 진행하고, 실제 데이터 규모 측정 결과를 바탕으로 조회·렌더링 최적화를 적용한다.
